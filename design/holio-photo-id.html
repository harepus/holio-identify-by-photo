Oslo Sprint 2026, Holio side challenge, pain 3

"Identify by photo" for Holio Ops

A fallback inside the Holio Ops scanner. When a pack has no barcode, a torn label or a code the register does not know, the worker photographs it and gets the product, counted exactly like a scan.

"Noen varer har ingen strekkode, en strekkode systemet ikke kjenner, eller en etikett som er revet av. Da må medarbeideren lete opp varen manuelt, og det er lett å velge feil. Mulig retning: kjenn igjen produktet fra et bilde eller fra teksten på emballasjen."Holio's brief, pain 3, 29 October 2026

The user is the warehouse worker at receiving, with a delivery on the floor and a handheld in one hand. The same fallback also opens in returns and in stock counts, where the same unknown pack shows up.

Design file for the build agent. Every screen, state and string below is the spec. Demo products are public Open Food Facts items (CC BY-SA), never customer data.

Why pain 3 is the most plug-and-play

Holio Ops is a React and TypeScript app in Capacitor. A pain is plug-and-play when Holio can drop one component and one endpoint in without changing what happens after. Pain 3 is the only open pain where the output is something Holio already accepts.

  1. It gives the same output as the scanner, a SKU, so nothing downstream changes.
  2. It runs only on the exception path. Normal scans keep their speed, and the model runs once per exception, not once per parcel.
  3. Holio passes context it already has: the PO lines in receiving, the sales order lines in returns, the location's products in counting. That cuts the search from the whole register to a handful.
  4. Link barcode fixes the data where the error enters the warehouse. The next pack with that code scans normally.
  5. It never blocks. An unsure answer becomes the top 3 plus "Search manually", which is today's path.
  6. Holio already has the two prerequisites: product images (Holio's product page says the images help identification) and the rebuilt macro camera scanner in 0.2.11.

How Holio plugs it in

One React component and one stateless endpoint. The component owns screens 3 to 7 and 9, plus the link-barcode sheet. Holio owns the scanner, the unknown-code sheet, the purchase order and the toast.

Component

<IdentifyByPhoto
  candidates={po.lines.map(toCandidate)}   // what the context already knows
  scannedCode={code}                       // optional, from the unknown-code sheet
  context="receiving"                      // "receiving" | "returns" | "counting" | "lookup"
  locale="nb"                              // "en" | "nb"
  identify={httpIdentify("/api/identify")} // or a function through Holio's own API client
  onConfirm={(r) => receiveLine(po.id, r)} // r = { sku, source: "photo", evidence }
  onLinkBarcode={(r) => linkCode(r)}       // r = { sku, code }
  onSearchManually={() => openSearch()}
  onDeviation={(r) => openDeviation(po.id, r)}
  onSearchRegister={(words) => searchProducts(words)} // optional, for screen 7
  contextLabel="PO #500004701"           // optional, used in titles such as "Not on PO #500004701"
  progress={{ received: 0, expected: 24 }} // optional, for "0/24 becomes 1/24"
/>

type Candidate = { sku: string; name: string; brand?: string; size?: string; image: string };
// onConfirm gets the same shape a barcode scan produces, plus source and evidence,
// so Holio feeds it into the handler it already has for a scanned line.

identify is a function, (request, signal) => Promise<response>, so Holio can route the call through the authenticated API client Holio Ops already has. httpIdentify(url) builds one for a plain URL. onSearchRegister is the one prop beyond the contract. Without it, a "none" answer goes straight to screen 9c, and screen 7 is skipped. With it, the component asks Holio for a text shortlist of the full register from the words the model read, and ranks that shortlist with a second call.

  • The model ranks the candidates and writes the evidence in the request's locale. Code decides the status with the rule the arena measured: none when the model says no candidate is this item, match when it picks one row, both self-checks pass (the variant words are on the pack, the size is settled) and its confidence is 0.7 or more, choose otherwise. Likelihood reaches the client as a word, "most_likely" or "possible", never a number.
  • Stateless. No database, no session, the photos are never written to disk. It logs status, candidate count and latency, never the photo.
  • Errors: 400 invalid_request, 401 unauthorized, 502 image_fetch_failed with the URL, 503 model_unavailable, 504 model_timeout at 22 s. The component shows screen 9b for all of them.
  • The engine is the arena's pain 3 winner: text read off the photo and image similarity shortlist, then a vision model picks one or abstains, with two self-checks (are the variant words on the pack, is the size settled). The product build calls the Claude API from the server instead of the macOS tools the prototype used.

Three steps for Holio

  1. Run the service as one container with their own model key in the environment.
  2. Map candidates from the context each flow already has: PO lines in receiving, the sales order's lines in returns, the location's products in counting.
  3. Mount the component on the scanner's unknown-code sheet and on the "No barcode?" link, and route onConfirm into the existing scan handler.

Limits

  • Groceries with printed text only. Apparel, parts and loose goods with little text are not measured, and those may be a large share of Holio's unbarcoded items.
  • Latency was measured on a shared Mac under load, not on a Zebra TC27 over warehouse Wi-Fi.
  • No real warehouse photos yet. The holdout is crowd-sourced photos. The real-photo set listed in the arena result is still open.
  • The judge is not deterministic. Two runs differed in one case.
